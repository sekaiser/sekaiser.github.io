CI/CD Across Team Boundaries

Published
03 Oct 2026
ci-cd software-delivery testing
On this page

Containerized applications can span several teams, repositories, and infrastructure accounts. Service tests alone do not coordinate delivery across those boundaries. This article presents a design that shares container-delivery mechanics, retains service-owned tools and checks, and bases deployment decisions on the tested service combination. Reusable GitHub Actions workflows build or reuse images, pass them between jobs, and promote them without rebuilding. A scenario-based testbench assembles selected services for recurring cross-service checks. An illustrative order change connects acceptance criteria, recorded test inputs, and rollout decisions. The design separates image reuse from fresh verification without assuming identical runtime behavior across environments. The discussion compares alternatives and makes the maintenance, access, and coordination costs explicit.

1 One change, several teams

Consider adding a delivery option to an order-processing application. The order API validates the request and publishes an acceptance event to an event stream. A consumer updates a query model, and the application displays the accepted order. Several teams may own those components, even though the user sees one operation.

For the engineer changing request validation, the task may look local. For the release owner, success requires a longer chain: the API accepts the new option, the event preserves it, and the query returns it with the correct order status. A service can pass its own tests while a downstream consumer drops the new field. Testing one boundary cannot establish the behavior of the whole chain.

The teams may also have different repositories, build tools, and release conventions. Some dependencies sit behind private networks or in separate infrastructure accounts. A useful pipeline has to work within those constraints, not assume that every team can replace its tooling or deploy everything together.

The same delivery work also recurs across applications: building an image, making it available to test jobs, publishing it to a registry, and deploying it with the right configuration. Copying those steps into each repository leaves each team maintaining its own version. The design shares that machinery and keeps behavioral checks with the service teams. Workflow maintainers own artifact handling; service teams own what their checks establish; platform owners control target access and deployment writes. A release decision depends on their combined work, not just a successful build.

The design described here uses GitHub Actions, Helm, and Kubernetes for the services it builds and deploys. Older systems can remain dependencies, with their own deployment procedures. The order change is an illustrative example, not a report of a company deployment. It gives us one thread to follow: what should change, which part of the platform we need to run, and what the pipeline must check before the new delivery option reaches customers.

2 What the test pyramid leaves to the pipeline

The test pyramid remains the starting point: many fast, narrow checks and fewer expensive checks of larger behavior [1]. Unit tests check request validation; integration tests exercise a broker or database; contract tests check what producers and consumers expect at a boundary. A missing delivery field may be caught there. A system scenario checks the remaining path from accepted request to query. This design does not replace those layers or run the whole application for every change.

A product-wide pyramid can include that scenario. What the pyramid does not specify is how separate repositories build the service images, select compatible versions, reach private dependencies, and retain a result that another team's deployment job can interpret. A balanced test suite still needs that machinery. If the consumer changes after the API's tests pass, the earlier result describes the tested combination, not necessarily the combination about to be deployed.

Agile practices address a different part of the problem. Teams agree acceptance criteria and integrate frequently. Scrum requires teams working on one product to share a Definition of Done [2]. The pipeline makes the agreed checks repeatable across repositories and infrastructure accounts; it does not replace those agreements.

3 Alternatives and their limits

Several approaches can reduce the work of cross-service verification. The choice is not between using them and having a shared pipeline:

  • A mock image for every service image. Mocks make dependencies cheap to run and help reproduce faults. Keeping their versions, state transitions, and event behavior faithful means maintaining another implementation. A passing test exercises that substitute, not the real image. Use mocks selectively rather than maintain a parallel catalogue of service replicas.
  • Verification from published API specifications. OpenAPI and AsyncAPI support checks of HTTP operations and messages [3, 4]; consumer contracts add expectations at individual boundaries [1]. Run these checks early. They do not by themselves establish that the API, broker, consumer, and query store preserve an express order before the deadline.
  • Service-owned pipelines and a few hand-written journey tests. This is the simpler baseline when cross-service changes are rare. As applications multiply, pipelines duplicate artifact handling and journey tests reconstruct the same setup. Share the repeated jobs first; add a maintained testbench when recurring journeys justify its cost.
  • A complete platform environment for every build. This can expose interactions a smaller setup omits, but includes unrelated services, data, credentials, and configuration. Sharing one such environment trades setup work for contention and changing versions. Keep broad regression, but use a smaller setup for feedback on a change to one delivery option.

4 Reuse delivery jobs across applications

The API team's repository calls a reusable GitHub Actions workflow [5]. It chooses a Dockerfile, optionally selects a service from a multi-service repository, and supplies build-relevant paths, test commands, chart values, and target settings. Shared workflows coordinate the jobs; smaller composite actions handle image transfer, registry operations, and deployment setup.

The common interface is an image and a set of commands, not one prescribed build tool. Compilation and packaging stay in the application's Dockerfile; test commands stay with the service. A single-image application and a repository with several buildable services can therefore use the same delivery jobs. Maintainers distribute changes through versioned workflow references rather than copy them into every application's pipeline.

Services keep cheap checks in their normal build and test entry points. Checks that require a running image consume the candidate selected by the workflow; they do not build another one for testing.

Developers can use the same test entry point locally and in CI. Each job names the checks it requires, and a skipped required check cannot count as success. If a broker or another prerequisite is unavailable, the job fails with that cause instead of silently reporting that the integration tests passed.

The workflow handles four repeated operations:

  • Build or reuse an image. It looks for an image for the requested commit, then for an ancestor whose declared build paths have not changed. Otherwise, it builds with a registry-backed layer cache. The run records the requested source commit, any reused image's origin, and the image digest.
  • Pass that image between jobs. An exported image archive and checksum let test and publication jobs load the same image on different runners. They verify the archive rather than compile the application again.
  • Publish after the selected checks pass. Integration and end-to-end commands remain service-owned. Every enabled check must succeed before publication; reusing an image does not exempt it from those checks.
  • Promote without rebuilding. Release jobs resolve the chosen source revision to an existing image, copy it to the destination registry, and check the destination digest. Helm deployment supplies the target's values and access. The artifact stays the same; its runtime configuration may differ.

Image reuse and layer caching avoid different kinds of repeated work. Reuse depends on declaring the complete source paths that affect the build, including shared code and generated inputs. Unchanged Git paths do not establish that mutable base images or external dependencies are still current; those need an explicit refresh policy. Required verification remains separate from the decision to rebuild.

One earlier workflow failure shows why the inputs need clear meanings. A pull request failed before building because a release-branch naming rule was applied to its feature branch. We changed the check to validate the pull request's target branch while keeping the source commit as the build identity. The release policy stayed intact, and developers could use ordinary feature names. The branch that determines whether a build is allowed is not the commit that determines what it contains.

Figure 1 follows the image through shared delivery jobs and no-rebuild promotion. Cross-service and target checks are enabled where the changed behavior requires them; image identity alone does not establish coverage of the proposed service combination and settings. The slim Run record rail supports that comparison, detailed in the run-record and release-decision tables below.

Runner placement follows the work, not the application language. A build or isolated test can run without access to private services; target checks and deployment need approved routes and credentials. Platform engineers maintain that access and the environment configuration so each application need not reconstruct the account and network setup.

The workflow can exchange a GitHub OpenID Connect token for short-lived cloud credentials [6]. That removes the need for long-lived cloud credentials in the job, but access still depends on which code and workflow are trusted. Untrusted change checks run without private-network reach, target credentials, or deployment authority. The target's operations owner approves the private-target execution path; its jobs use isolated runners and scoped roles. Test access stays separate from permission to deploy to production [7].

5 Start with the behavior

The API and consumer teams first agree what accepting an express order means. The request must be valid, the acceptance event must retain the delivery option, and the query must show the accepted order before a deadline. Those expectations belong beside the code review, even when the scenario lives in a separate testbench repository.

The test matches the unique order reference across the request, event, and query response. An accepted order from yesterday cannot make today's run pass. The deadline starts when the request is submitted; the test waits for asynchronous processing, but fails if the expected result never arrives.

This scenario checks the first matching accepted result. If the requirement also covers duplicate events, another scenario must replay the event and check the order after the consumer has processed it.

One implementation of this acceptance stage uses spex, which translates constrained scenarios through a maintained catalog into Kubernetes Test TooL (KUTTL) workspaces [8]. Each step needs a matching catalog entry. Unsupported steps fail validation; new kinds of checks need reviewed catalog or probe changes. The pipeline invokes the testbench as a test command supplied for the acceptance stage.

6 Build the part of the platform you need

The order scenario needs more than the API, but less than the whole platform. It needs the event stream, the consumer, and the query service and its store. Authentication or customer services also belong in that setup if the request depends on them. Unrelated applications need not run just because they share the same platform or organization.

For this stage, teams assemble a repeatable slice around the behavior being checked: selected scenarios, participating services and dependencies, configuration, test data, and observations. Its boundary follows the use case, domain, or capability, not necessarily a repository or a team's service boundary.

The example tags group express delivery by use case, orders by domain, and order acceptance by capability. Those views can overlap and share setup; they do not imply separate stacks. Teams define the labels, not spex. Tag filtering does not discover dependencies or remove services from the setup; teams maintain that boundary.

That boundary matters when interpreting a result. A fixture can show how the consumer handles a selected response; a check against the real dependency is needed to learn whether it actually returns that response. A small order slice can establish the delivery-option behavior without establishing every production interaction or the platform's behavior under load. Review deployments need pipeline-owned access and lifetime management as well as a suitable slice.

6.1 Optional implementation with spex

The spex testbench separates scenario selection from application setup [9]:

  • A suite selects scenarios; its entries can choose different profiles.
  • A catalog defines the supported scenario operations.
  • A binding supplies endpoints and secret references.
  • A profile defines the application setup and can extend a shared cluster base.

The order profile installs the API, consumer, query service, broker, and store. The pipeline supplies the candidate API image and pins companion versions; the binding points probes at those installations. The suite also names any customer service reached outside the slice.

A replay check can use a narrower profile when its consumer does not call the API. It seeds an order and event for that run, then exercises the broker, consumer, query service, and store using the same cluster base. A domain suite can include both checks without requiring identical application stacks.

The resolved plan and generated workspace expose the selection and setup for review. For a local or CI run, a profile can start a temporary Kind cluster and install the chosen services; Kind runs Kubernetes nodes in containers [10]. For shared development services, the binding points to existing installations and the matching profile creates only test-owned resources.

7 Know what a passing test covered

Suppose the order scenario passes. The event retained "express", and the query returned the accepted order before the deadline. To use that result later, we need to know which API and consumer produced it, which settings were active, and whether the probes exercised the intended services.

The pipeline therefore keeps a record of the run:

Table 1: Run record for coverage comparison and failure investigation.
Part of the run Scope Recorded information
Build Source Requested commit; reused-image origin
Build Artifacts Image and chart digests
Build Execution Resolved workflow and action revisions; run identity
Test setup Checks Commands; selected checks; tool revisions
Test setup Testbench Suite, catalog and profile revisions where used
Target Services Actual service versions; binding revisions
Target Configuration Settings; flags; secret version references
Test data Identities Fixture and seed IDs; unique run-specific order reference
Result Observations Requests; matching event and query observations; time window
Result Diagnostics Reports and diagnostics

Resolve artifact tags to content digests and workflow references to commits. The runner checks actual deployments and settings against the recorded setup; recording what a job intended to deploy is not enough. These details help reconstruct failures, although data from an external service may need to be modeled in a regression test rather than reproduced exactly.

7.1 If deployment approval uses a shared target

Use an isolated slice when the required services can be recreated. Only where access or infrastructure constraints require a shared target does this branch apply. Another team may replace the consumer while the test runs: the order assertions might pass without establishing which combination produced the result. Version checks before and after the test also miss a temporary replacement between those snapshots.

If a shared, changeable target supplies release evidence, the platform must control competing writes. Each run reserves the resources that affect its assertions from deployment through result collection. Participating jobs use the same control across repositories; a repository-local concurrency group cannot provide that scope. The platform team operates it with the affected teams and account owners.

A worker-side check is insufficient. Job A may pass it, pause until its reservation expires, and resume after job B changes the consumer. The target must reject A's stale authority when it accepts deployment writes. It must also reject competing writes during a valid reservation, and participating jobs must have no alternate write path. This is a requirement on the surrounding platform; neither spex nor a reusable workflow alone supplies it.

The runner also watches the participating deployments and relevant settings. A detected change, a lost reservation, or a gap in those observations makes the run unusable for approving deployment, even if the order checks passed. Waiting deployments, out-of-band replacements, and resumed stale jobs are cases to exercise when checking the pipeline itself.

This control has a boundary too. An administrator may bypass it, and an external service may change without exposing a version we can observe. The suite names those dependencies and uses isolated test identities or disposable targets where shared data would confuse the result. A reservation does not freeze a database or turn an external service into a reproducible fixture.

7.2 Keep reports tied to the image

Test tools produce reports; spex, for example, collects scenario and suite results with JUnit output for CI [8]. Shared jobs tie those reports to the image, check versions, and integrate with the platform's deployment controls. The deployment job accepts records only from approved build and test runs, linked to the image and stored where another job cannot replace them. It checks that origin before trusting a report. Export allowlisted configuration and redact credential-bearing fields in captured requests, responses, and logs.

When a run fails, the observations give investigation a starting point. Did the API reject the request, did the event lose the option, or did the consumer never update the query? Those are different failures from an unavailable broker or a wrong endpoint. The initial diagnosis may change as more information arrives, but the engineer should not have to infer the whole path from a red CI badge.

8 Deploy the combination that was checked

Before deploying, compare the proposed service combination and settings with the recorded coverage. Include intermediate rollout states, not just the final versions. If coverage is missing, obtain a relevant result or run the checks.

Consider one illustrative decision. A2 names an API image digest; C1 and C2 name different consumer image digests. The express option stays enabled, and the remaining declared inputs stay fixed.

Table 2: An illustrative release decision for an unchanged API image.
Stage Combination Decision
Recorded pass A2 with C1 Retain coverage of A2/C1
Later proposal A2 with C2 Hold pending coverage of A2/C2
Rolling proposal A2 with C1, C2 Cover both paths and their coexistence

The original pass still describes A2/C1; it does not establish A2/C2 merely because the API image stayed unchanged. A test that happens to reach C1 during a mixed rollout says nothing about the C2 path. The release owner needs coverage of each required path and their coexistence.

The comparison must hold when deployment starts, not just when someone opens the approval screen. The deployment control checks those versions and settings on the target and prevents competing jobs from changing them while deployment proceeds. The development environment need not stay locked while production approval waits.

Reusing evidence does not require identical environments. Service teams identify the settings each acceptance claim depends on: feature flags, event formats, consumer modes, storage-schema expectations, and any timeout or retry policy behind a deadline. The rollout must use the tested values or have explicit coverage of the alternatives. If configuration changes without explanation, verify it; do not assume it is harmless.

Endpoint addresses and secret references may differ under a reviewed substitution policy. Keep them in the record, then check routes, authentication, and intended service identities on the target. Those checks show that the substituted configuration reaches the expected services; they do not extend the behavioral coverage to untested flags, formats, or processing modes.

Where a required external service exposes no version, the record shows what it returned during the test, not that it will behave the same at deployment. The person approving release must address that limit with a relevant target check or an explicit risk decision under the exception policy.

8.1 Roll out and recover the express-order change

For the express option, the teams agree a sequence. First deploy a consumer that handles existing events and preserves the new field. Test it with the current producer and then with the new producer. If old consumer instances will remain active, check the new producer with them too; otherwise, keep the new option disabled until they have left service. Compatibility includes older stored records and replayed events, not just newly submitted orders.

For a replay check, the test must observe processing progress before checking the order. An unchanged query response read before the consumer handles the replayed event says nothing about replay behavior. The teams agree how to observe completion rather than leave that choice to the step implementation.

The release coordinator needs the affected teams to agree on those combinations and on how long older formats remain supported. The target operator must be able to stop the rollout. If teams disagree about support, priority, or acceptable risk, a named authority must settle it; a workflow cannot. The same applies to exceptions: policy names who may approve them, and the decision records the scope, unresolved risk, and accountable person. An exception does not make a failed or inapplicable test result pass.

During activation, the operations owner watches the delay from acceptance to query and the consumer backlog against agreed stop conditions. Exceeding them holds further activation and starts recovery. Turning off the option or limiting traffic may contain the problem, but orders already accepted still need processing or repair. Redeploying an earlier image cannot undo database writes or recall events already in flight.

If a customer later selects express delivery but sees the standard option, investigation should produce both a correction and, where practical, a regression scenario. The scenario belongs in the relevant slice, so the next engineer can exercise that failure without reconstructing it from messages and memory. That improves the next change; it does not replace immediate recovery.

9 Keep the shared setup worth maintaining

A slice makes the test scope explicit, but it still needs maintenance. The teams responsible for the order behavior agree its scenarios and keep track of affected consumers and required checks. Tags help organize the scenarios; they are not an automatic analysis of what a code change can break. An incomplete dependency map can leave out the very consumer that needed checking.

Shared state also limits parallelism. Independent scenarios may run together, but different builds using the same reserved resources need isolated targets or must wait. More runners do not remove that queue. If waiting or repeated invalidated runs dominate feedback time, the teams need a smaller shared scope, more isolation, or fewer coordinated runs. A test that changes shared data needs exclusive access or a disposable target. Cleanup removes only resources owned by the run, not infrastructure that was already there.

The people maintaining the catalog and setup also own the diagnostics. Generated workspaces and execution plans must stay readable. Otherwise, a simple scenario merely transfers work to the engineer investigating its failure. New assertions, service versions, profile changes, and workflow upgrades need time in the teams' plans, not just names in an ownership table.

Adoption can start with shared build and test jobs, then add a slice for a recurring cross-service check. Consumers choose supported workflow versions and an upgrade policy. Commit references pin revisions; moving release tags require each run to record the resolved commit. Maintainers check changes against representative services, including unusual build and access requirements. Teams agree which workflow and record versions deployment jobs accept; an old revision's output does not remain supported indefinitely. Separately referenced actions need the same upgrade policy and resolved-commit record; pinning the workflow does not pin those actions.

Assess shared delivery jobs and the testbench investment separately: repeated build and setup work, defects found, debugging effort, deployment queues, and runner and maintenance costs. A faster build can simply move work into manual diagnosis. Comparable observations are needed before claiming the whole process improved.

For the order change, shared jobs handle the artifact, the selected slice checks the request-to-query behavior, and deployment checks whether the proposed rollout falls within that coverage. Teams retain their Dockerfiles and test commands while sharing the jobs that build, transfer, verify, and deploy their images. Approve the covered service combination, not an isolated green build.
