The Iterator Is the State Machine

Published
26 Oct 2026
rust iterators api-design
On this page

I can read a chain of enumerate(), filter(), and take() and understand what it asks for. I find it harder to picture what is actually running. Does each step traverse the data again? What does the chain borrow, and what work stops when we stop asking for values?

We'll build a small adapter, extend the pattern to prefix sums, and follow a query over borrowed telemetry records. The aim is to understand how the Iterator contract lets these pieces compose, and how ownership and dispatch affect the code we can write. That also gives us a basis for deciding when an ordinary iterator is enough and when asynchronous streams or coroutines help.

C++ ranges provide a useful comparison because they support lazy composition too. Looking at both languages helps distinguish the techniques they share from Rust's compile-time checks on borrowing. This gives us a way to judge the safety and potential costs of an iterator-based design, including which performance claims still need measurement.

How Rust iterators work

The output starts at 0: 1 and ends at 3: 4. Somewhere, something remembers which value comes next and which index to attach to it.

Rust's iteration protocol puts that responsibility in the iterator. Its required interface is small:fn:1

A trait describes behavior a type can provide. Here, Item names the type of value it produces. next() asks for one value and returns either Some(value) or None. The &mut self parameter lets the iterator change its own state while answering.

A for loop first asks IntoIterator to turn its input into an iterator, then repeatedly asks for the next value. For this simple array, we can sketch the loop like this:fn:2

The loop stops at the first None. It doesn't need to know whether advancing means moving through an array, following a list, or reading from a file.

Does None always mean the iterator has finished forever?

The Iterator contract allows an implementation to return Some again after returning None. A for loop still stops at that first None. If you need later calls to keep returning None, fuse() supplies that behavior. Iterators implementing FusedIterator already promise it.fn:3

This becomes relevant when we reach asynchronous streams: None is not a general-purpose instruction to wait and try again later.

Composing iterators with adapters

An adapter wraps an iterator and implements Iterator itself. That shared interface lets us connect adapters: each one can use another as its source, without knowing how that source obtains its values.

Because Indexed<I> also implements Iterator, it gets the trait's provided methods, including filter() and take().

The ? after self.source.next() returns None immediately if the source returned None. Otherwise, it extracts the value. We save the current index, increment the counter for next time, and return the pair.

Rust's standard-library Enumerate stores the same two pieces of state. It also implements shortcuts for operations such as nth(), fold(), and try_fold(). We will come back to why those matter.fn:4

A counter still has a limit

The example uses usize, just as Enumerate does. Its index can overflow on a sufficiently long sequence. The public enumerate() documentation says that enumeration can panic or produce an incorrect count when the counter overflows, with a panic guaranteed when overflow checks are enabled. This adapter is a model of ordinary enumeration, not an arbitrary-precision counter.fn:5

Prefix sums

The same structure can produce prefix sums. Keep a running total alongside the source, add each incoming value, and yield the new total. For 3, 1, 4, 2, the prefix sums are 3, 4, 8, 10.

This time the bound is narrower: the source must produce u64 values so we can add them to the total. The adapters after it still work through Iterator. enumerate() numbers the sums, and take(3) stops the chain before the last input is read. Neither needs to know how PrefixSums maintains its total.

As with the index counter, a reusable numeric adapter needs a policy for overflow. These small sums fit in u64. The standard library also provides scan(), which can express the same running total using stored state and a closure.fn:6

Ask for two matches

Now suppose we want the first two even values and their positions in the original input:

enumerate() produces pairs. filter() keeps pairs whose value is even. Its predicate borrows each item as &Self::Item to test it; an accepted item is then passed on by value. With borrowed source items, that test adds another layer of references.fn:7 take(2) allows at most two items through, and collect() gathers them into a vector.

It is easy to imagine a separate pass at every dot: number all five values, put the even ones somewhere, then copy the first two. These adapters can instead pass requests and values through the chain without building those intermediate collections.fn:8

Think of asking the outer iterator for a match. It asks its source, which eventually reaches the array. The value 10 comes back with index 0, passes the filter, and becomes the first result.

The second request takes more work. 11 gets index 1 but fails the filter. The filter asks again, receives (2, 12), and accepts it. Once take(2) has supplied two results, it stops asking the source for more.

The last two values aren't pulled through inspect(). Constructing the adapter chain didn't scan the input; consuming it caused the work. The final vector has storage of its own, but there is no vector between each adapter.

There is a limit to this control. Asking for one output can require examining many inputs. A filter over an infinite sequence with no matches never returns a match. Calling take(2) limits the number of outputs; it does not promise two source reads, a time limit, or a bounded amount of work.

Keep the records where they are

Numbering works the same way whether the source produces owned values or references. The difference travels through Item:

Expression Item type What the loop receives
names.iter() &String A shared reference to each string
names.iter_mut() &mut String An exclusive reference to each string
names.into_iter() String Ownership of each string from this vector

Here are all three with the same adapter:

The last loop moves the strings out of the vector. It doesn't clone their contents, and we cannot use names afterward as though it still owned them. In the earlier loops, Rust checks that uses of the references respect their lifetimes and exclusive access requirements.fn:9

enumerate() doesn't need separate code for each case. Its pair contains I::Item, whatever that happens to be. It adds a counter while leaving the ownership relationship intact.

Ownership also determines cleanup. When we drop an adapter, its owned fields are dropped too, including the source iterator and any closure state. If a chain consumes a vector with into_iter(), dropping it also drops the vector iterator's unconsumed elements. A chain built with iter() only borrows the vector; dropping that chain leaves the elements in place.fn:10 Early termination stops further pulls, but cleanup can still do work.

The lifetime label 'a ties the references in the results to the borrowed input. It doesn't extend the life of the buffer or copy it somewhere safe. If a caller tries to keep using the search after the readings have gone away, the program fails to compile.

The move keyword makes the closure capture threshold_ms by value. Because u32 implements Copy, the closure stores a copy of the threshold instead of borrowing the function's local variable. The readings remain borrowed through the source iterator.fn:11

Keep a result while asking for another

Using the same readings, we can retain two matches and drop the search before using them:

Each call briefly borrows the iterator mutably so it can advance. The returned references borrow readings, not the iterator object. Holding the first result doesn't keep that call's mutable borrow of the iterator open, so we can ask for another. Dropping the iterator leaves both references usable as long as the underlying readings remain valid.fn:12

The signature separates these lifetimes. Item is fixed for the iterator type; it isn't parameterized by the temporary borrow of each next() call. In this search it contains &'a Reading, with 'a tied to the input slice. A mutable iterator must also make it safe to retain several results, for example by yielding references to distinct elements.

That is a limit on what ordinary Iterator can express. It cannot generally lend out a reference into its own scratch buffer and then overwrite that buffer on the next call while the reference is still in use. Such an API needs a different ownership arrangement, or a lending-style contract that ties each result to the call's borrow. We don't need that here: the caller already owns the buffer.

impl Iterator hides a concrete return type that would be awkward to write out. The compiler still knows that type, including the closure and the wrapped iterators. Returning it this way does not introduce a boxed object or a virtual method call.fn:13

Static and dynamic dispatch

The trait tells us what an iterator can do. Rust lets us choose how a call reaches the implementation. Here are two functions asking for the same thing:

With next_static, the compiler knows the concrete I and can specialize the function for it. This is static dispatch.fn:14 With next_dynamic, the function accepts a trait object. Its reference carries a pointer to the iterator state and vtable metadata used to find the method at runtime. This is dynamic dispatch.fn:15

The iterator still holds its state in either case. Dispatch changes how we reach the method, not who drives the sequence or whether it is lazy.

Notice that next_dynamic borrows an iterator. It doesn't allocate one. We can pass a reference to an iterator already stored in a local variable. Heap allocation and dynamic dispatch are separate choices.

For our telemetry query, each adapter and closure has a concrete type. suspicious() returns the resulting chain through impl Iterator, which hides its name without erasing that type. The compiler keeps the information needed to specialize calls and consider inlining them.fn:13 We haven't needed a runtime choice of implementation between stages.

A concrete wrapper can still contain a dynamically dispatched iterator. Adding take() around a trait object doesn't make calls to that underlying source static.

When would a boxed iterator be useful?

Suppose a query can return every value or only even ones, depending on a setting read at runtime:

The branches construct different types: one includes a filter and the other doesn't. Box<dyn Iterator<Item = u64> + 'a> gives them a common return type. The box owns the iterator state; the slice remains borrowed. The lifetime bound keeps that borrow valid, and Item = u64 tells callers what either implementation produces.

A plain impl Iterator return cannot hide a different concrete type in each branch. For this particular condition we could instead use one filter with a configurable predicate. An enum could also represent a fixed set of alternatives. A trait object becomes useful when we want a common interface without making that set part of its type.

Here the box supplies owned heap storage for the iterator, not a newly allocated record on every call. The earlier &mut dyn Iterator example supplies dynamic dispatch without that storage choice. Both retain the usual ownership and borrowing checks.

Static specialization can increase generated code size and compilation work when many concrete types use the same generic code. Dynamic dispatch can let a consumer share one implementation across those types. An indirect call may make inlining harder, although the optimizer can sometimes recover the target. If this trade-off matters to the application, it needs measurement.fn:14, fn:16

Which iterator methods can a trait object call?

Traits must satisfy Rust's dyn compatibility rules to support trait objects. Iterator does, once we specify its associated Item type. Its next() method can be called through the vtable. Many generic adapter and consumer methods instead require Self: Sized, which excludes those methods from the dynamically callable interface.fn:17

That doesn't prevent further composition. A sized wrapper such as Box<dyn Iterator<Item = u64>> or &mut dyn Iterator<Item = u64> itself implements Iterator. We can add adapters around it. The outer adapter has a concrete type, while requests reaching the erased source still use its dynamic interface. A generic wrapper doesn't automatically make every call inside it static.fn:1

For a visual tour of trait-object pointers, see Sofía Belén López Vicens's Visualizing Rust's VTables: How dyn Trait Works in Memory. Exact byte layouts and vtable slot offsets should not be treated as a stable Rust ABI.fn:18

Compiler optimization

An iterator chain can compile to code similar to a hand-written loop. Rust specializes generic code for concrete types through monomorphization. Inlining can then bring operations from different adapters together so the optimizer can work across them.fn:14

For example, these functions calculate the same sum. The wrapping operations make overflow behavior explicit:

Inlining and loop optimization can make the generated code resemble the handwritten version. Whether they do so for a particular program depends on the compiler, target, optimization settings, and surrounding code. We would have to inspect that output and benchmark representative inputs to make a performance claim.fn:19

There is another wrinkle in our request-by-request picture. The standard library can implement a consumer such as fold() by passing the whole accumulation through the adapters. Its Enumerate implementation has specialized fold() and try_fold() methods, so consuming a chain need not literally become a tower of next() calls. The pull model explains the sequence's behavior; optimized bulk operations can implement it differently.fn:4

Some costs are visible without a benchmark. Our simple adapter chain doesn't require an intermediate collection at every step. It uses concrete types instead of a required virtual call at every boundary. Neither fact makes the predicate free, guarantees vectorization, or eliminates allocation in user-supplied code.

In Fast Writes, Fresh Reads, moving work into a background thread introduced replay and coordination costs. Here, calling filter() doesn't start a worker at all. The caller runs the predicate as it consumes the iterator. A fluent chain of methods doesn't, by itself, tell us where computation runs.

Asynchronous iteration and coroutines

The telemetry example starts with a slice already in memory. A live connection has another possibility: there is no new reading yet, but more may arrive.

An ordinary iterator can block inside next() until data arrives. Its interface doesn't say whether a call will return quickly. What it lacks is a way to return "not ready" together with an asynchronous wakeup arrangement.

The Stream trait from futures-core adds that distinction:fn:20

Result Meaning
Ready(Some(value)) A value is available
Ready(None) The stream has ended
Pending No value yet; arrange a wakeup when progress may be possible

Context gives the implementation access to a waker. Pin supports implementations whose state must stay at a stable location while pinned. Those requirements serve asynchronous execution, beyond the in-memory loop we started with.fn:21

Rust's async computations use the Future protocol. The compiler represents their progress in a generated state machine, retaining what is needed across an await.fn:22, fn:23

A coroutine lets a function suspend and later resume from where it stopped. A synchronous generator uses that ability to yield values one at a time, with its consumer requesting each resumption.fn:24

When producing a value involves nested loops and several yield points, that can be easier to follow than a hand-written state machine. Our numbering adapter needed only a source and a counter; more complicated control flow can justify the extra mechanism.

There is also a boundary between local demand and system backpressure. A caller can stop pulling this iterator while a device, broker, or network buffer keeps receiving data. The capacity, loss, and admission policies from Backpressure in a Telemetry Pipeline still need to exist outside the iterator. A take() at the end of a chain doesn't bound every queue upstream.

Iterator composition in C++

C++ ranges let us build a similar lazy pipeline, so they give us a way to ask which parts of the design are specific to Rust. C++23 provides enumeration directly:fn:25

C++20 ranges already offered lazy composition; C++23 added this standard numbering adapter. Comparing a small Rust enumerate() call with the plumbing of a hand-built C++ coroutine generator would measure two different implementation choices.

C++ ranges use iterator and sentinel interfaces, concepts, and views. A sentinel marks the end condition; it need not have the same type as the iterator. Those interfaces support lazy computation and compiler optimization too. Rust doesn't have exclusive access to that technique.

Both languages support references, moves, and deterministic destruction. Rust's borrowing rules add compiler checks for reference lifetimes and exclusive access across the composition. C++ APIs can express ownership and borrowing relationships, but ordinary references don't generally carry the same static checks. The borrowing example is where I find the comparison most useful: who must establish that these records are still valid when a result is used?

Choosing the mechanism

We can now account for the numbered loop. The source remembers its position. Enumerate remembers a counter. A filter may ask several times before passing a value along. The consumer decides whether to keep asking, and the item type preserves whether the result owns or borrows its data.

For a query over an existing buffer, returning a borrowed iterator lets the caller inspect a few matches without first building a collection. If obtaining the next value requires waiting for a socket, an ordinary iterator can block inside next(). When the caller must yield execution while waiting and resume when progress becomes possible, the interface needs an asynchronous readiness and wakeup protocol. If later work needs to revisit or sort the results, collecting them may be the right choice.

When I read an iterator chain now, I try to picture the state each adapter holds and the work one request can trigger. That gives me a way to judge the abstraction before making assumptions about its speed.
